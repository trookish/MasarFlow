# MasarFlow — Python Integration Analysis

## Project Context

MasarFlow is a **local-first, AI-native project workspace** (Next.js 16 / React 19 / Dexie-IndexedDB). All domain data lives in the browser. The AI layer uses a `/api/chat` proxy to OpenAI/Anthropic, with an **in-browser agentic loop** (`runWorkspaceChat`) that executes ~40 tools against local Dexie repos. A 16-step idea→implementation workflow pipeline, a 7-agent roster, a React Flow canvas, a d3-force knowledge graph, Obsidian/GitHub sync, and a filesystem watcher round out the feature set.

The opportunities below are ordered by **priority score** (impact × feasibility), grouped into tiers.

---

## TIER 1 — Transformative (Priority 9–10)

### 1. Semantic Search & Embedding Pipeline
**Location:** `src/lib/utils/search.ts`, `src/components/search/search-view.tsx`, `src/components/shell/global-search.tsx`, the `search_workspace` AI tool in `src/lib/ai/tools.ts`

**Why Python fits:** The app labels its search "semantic" but it's **Fuse.js fuzzy string matching** — no embeddings, no vectors, no inverted index. Python is the undisputed ecosystem for real semantic search: `sentence-transformers` for embeddings, `chromadb`/`qdrant`/`FAISS` for vector stores, and proper tokenization pipelines. This is the single biggest gap between the product's promise and its implementation.

**Use cases:**
- Embedding generation for all notes, specs, tasks, docs, devlogs, memories (8 entity types currently flattened into `SearchItem[]`)
- True vector similarity search (cosine/HNSW) replacing Bitap fuzzy matching
- Hybrid search (BM25 keyword + dense vector) with reciprocal rank fusion
- Re-embedding on content change (incremental, debounced via watcher)
- Cross-encoder reranking for precision

**Integration approach:** A **local FastAPI microservice** running `sentence-transformers` (e.g., `all-MiniLM-L6-v2` for speed, or `bge-small-en` for quality) + a persistent `chromadb` collection. The Next.js `/api/chat`-style proxy pattern is already established — add an `/api/search/semantic` route that calls the Python service. Embeddings are generated by a **background worker** (Celery/RQ or a simple `asyncio` queue) that the Next.js app notifies on DB writes via a small webhook. The vector store holds `{id, kind, projectId, embedding, payload}` mirroring the Dexie entities. The browser's `buildSearchItems` call would be replaced with a fetch to the Python service.

**Priority: 10/10** — Closes the biggest feature gap; directly improves the core search UX, the global command palette, the `search_workspace` AI tool, and the context engine's `pickFullBodies` relevance selection.

### 2. RAG Context Engine (Retrieval-Augmented Generation)
**Location:** `src/lib/ai/context.ts` (`fetchWorkspaceSnapshot`, `formatWorkspaceContext`, `assembleWorkspaceContext`, `buildAssistantSystemPrompt`)

**Why Python fits:** The current context engine dumps the **entire workspace** (all notes, specs, tasks, systems, memories, docs, commits, devlogs) into a ~28,000-char markdown blob, using Fuse.js to pick 6 "most relevant" note/doc bodies for full inlining. This is brute-force context stuffing. Python's RAG ecosystem (`langchain`/`llama-index` retrieval, chunking strategies, reranking, query expansion) would transform this into intelligent, query-aware retrieval that fits in the model's context window with far higher signal-to-noise.

**Use cases:**
- Semantic chunking of long notes/docs (paragraph-aware, overlap-windowed) instead of 4,000-char clips
- Query-aware retrieval: embed the user's query, fetch top-k relevant chunks across all entity types
- Multi-vector retrieval (hybrid: BM25 + dense + metadata filters like `kind`, `tags`, `specId`)
- Context window budgeting with reranking (cross-encoder) and compression
- Conversational memory management (summarizing old turns, sliding window)
- Query rewriting/expansion for the 16-step workflow (each step's `buildStepPrompt` could retrieve differently)

**Integration approach:** A **FastAPI service** exposing `/rag/query` that accepts `{projectId, query, topK, filters, budgetChars}` and returns ranked context chunks. The browser's `assembleWorkspaceContext` would call this instead of fetching all 11 repos and formatting locally. The Python service maintains its own vector store (synced with Dexie via the embedding pipeline from opportunity #1). For the workflow pipeline, each step's `buildStepPrompt` could call the RAG service with step-specific retrieval strategies.

**Priority: 10/10** — Every AI feature (chat, agents, workflow) depends on this context. Better retrieval = better AI output across the entire product. This is the force multiplier.

### 3. Local LLM Inference Server
**Location:** `src/lib/ai/catalog.ts` (`FALLBACK_CATALOG`, `fetchCatalog`), `src/app/api/chat/route.ts`, `src/lib/ai/chat-client.ts`

**Why Python fits:** The app is **BYO-key** — users must supply an OpenAI/Anthropic API key. A local Python inference server (Ollama, llama.cpp Python bindings, or vLLM) would let users run models entirely offline, with no API costs, no data leaving their machine. This aligns perfectly with MasarFlow's **local-first philosophy**. The catalog already supports OpenAI-compatible providers — a local server is just another `AiConnection` with `baseUrl: http://localhost:11434/v1`.

**Use cases:**
- Zero-config local AI (no API key needed — the strongest onboarding improvement possible)
- Private/sensitive project data never leaves the machine
- Cost-free unlimited agent runs and workflow pipeline execution
- Model serving for embedding generation (opportunity #1) and reranking (opportunity #2)
- Fine-tuned/specialized models for code generation, spec writing, etc.

**Integration approach:** An **Ollama server** (already Python-compatible, OpenAI-compatible API) running locally. The catalog's `providerBaseUrl` and `providerFormat` already handle OpenAI-compatible endpoints. Add a "Local" provider to `FALLBACK_CATALOG` pointing to `http://localhost:11434/v1`, with auto-detection of available models via Ollama's `/api/tags` endpoint. The `/api/chat` proxy already forwards to any OpenAI-compatible base URL — **zero changes needed to the streaming/proxy infrastructure**. A Python **companion daemon** (FastAPI) could manage Ollama lifecycle (start/stop, model pulling, health checks) and expose a unified `/local/models` endpoint.

**Priority: 9/10** — Removes the biggest barrier to entry (API key requirement); aligns with local-first ethos; enables all other Python AI opportunities to share one runtime.

### 4. Code Analysis & AST-Based Standards Enforcement
**Location:** `src/lib/enforce.ts` (`runEnforcer`, `compileStandardPattern`), `src/components/standards/enforcer-panel.tsx`, `src/components/standards/standards-view.tsx`, the `computeTechDebt` metric in `src/lib/metrics.ts`

**Why Python fits:** The current Standards Enforcer is **pure regex pattern matching** against note/spec/task markdown content. It can't parse code, understand control flow, or detect semantic violations. Python's `ast` module, `pylint`/`flake8`/`ruff` for Python, `tree-sitter` (multi-language AST parsing), and `bandit` (security analysis) would turn this into a real static analysis engine. The tech-debt metric currently counts regex violations — it could reflect real code quality.

**Use cases:**
- Multi-language AST parsing (tree-sitter supports 50+ languages) of files caught by the Watcher
- Real linting: complexity metrics (cyclomatic, cognitive), dead code, unused imports, security smells
- Pattern-based architectural rule enforcement (e.g., "no direct DB access in UI components" via import-graph analysis)
- Dependency graph extraction from actual source code (imports, calls) — feeds the Architecture diagram
- Diff analysis on Git commits (what changed, what patterns were introduced)
- Automated code review comments (feeding the `reviewer` agent)

**Integration approach:** A **FastAPI service** exposing `/analyze` (file content → violations/metrics) and `/ast/graph` (directory → dependency graph). The Watcher's `/api/watch` SSE route already streams file events — a Python **background worker** could subscribe (or be notified via webhook), parse changed files, and write `WatchEvent`-enriched analysis results back through a small API. The `runEnforcer` function would call the Python service for code files and fall back to regex for markdown. The `computeTechDebt` metric would query the Python service for real complexity/violation counts.

**Priority: 9/10** — Transforms the enforcer from a toy regex matcher into a real static analysis tool; gives the architecture diagram real dependency edges from code; feeds the reviewer agent actionable findings.

## TIER 2 — High-Impact (Priority 7–8)

### 5. Knowledge Graph Analysis Engine
**Location:** `src/components/brain/knowledge-graph.tsx` (d3-force simulation), `src/lib/db/repos/links.ts`, `src/lib/db/schema.ts` (`Link`, `EntityKind`), `src/components/brain/backlinks-panel.tsx`

**Why Python fits:** The knowledge graph currently runs a **d3-force layout simulation** and renders nodes/edges. There's no graph analysis — no centrality, no community detection, no pathfinding, no link prediction. Python's `networkx` is the gold standard for graph algorithms, and `graphrag`/`igraph` add specialized capabilities. The graph stores typed edges (`wikilink`, `dependency`, `reference`, `implements`, `relates`) across 8 entity kinds — rich material for analysis.

**Use cases:**
- **Community detection** (Louvain/Greedy modularity): cluster notes/specs/systems into emergent themes — auto-suggest folders or architecture groupings
- **Centrality analysis**: identify the most connected/important specs/notes (PageRank, betweenness) — surface "hub" documents
- **Link prediction**: suggest missing connections ("note A and note B reference similar concepts but aren't linked — create a `[[wikilink]]`?")
- **Shortest path / influence tracing**: "how does this spec affect this system?" — trace dependency chains
- **Graph summarization**: auto-generate a "project architecture overview" note from the graph structure
- **Cycle detection** in system dependencies (the `arch-layout.ts` already has a cycle guard for layout — Python could detect and report these)
- **GraphRAG**: community-based retrieval (Microsoft's GraphRAG approach) for the RAG context engine

**Integration approach:** A **FastAPI service** exposing `/graph/analyze` (accepts the `links` + entities as JSON, returns analysis results). The browser's `KnowledgeGraph` component calls it on mount/graph-change (debounced). For the link prediction, a **background worker** periodically recomputes suggestions and writes them to a `LinkSuggestion` table (new Dexie entity). Community detection results could auto-create `Folder` groupings or suggest architecture `System` categories.

**Priority: 8/10** — Turns the graph from a visualization into an analytical tool; the link-prediction alone would meaningfully improve the "second brain" experience; GraphRAG integration amplifies the RAG engine (#2).

### 6. Background Worker Queue (Embeddings, Sync, Analysis, Indexing)
**Location:** Cross-cutting — the watcher (`/api/watch`), sync (`sync-view.tsx`), embedding pipeline (#1), code analysis (#4), GitHub sync (`github-sync.ts`)

**Why Python fits:** MasarFlow currently has **no background processing**. Everything runs in the browser or in a Next.js request lifecycle. Embedding generation, file parsing, code analysis, graph computation, and sync reconciliation are all CPU/IO-heavy tasks that shouldn't block the UI or the request-response cycle. Python's task queue ecosystem (Celery, RQ, Dramatiq, or even `asyncio` with a simple queue) is purpose-built for this.

**Use cases:**
- **Embedding generation**: batch-embed all new/modified notes, specs, docs when content changes
- **Code analysis pipeline**: parse files caught by the watcher, run AST analysis, update violation metrics
- **Graph recomputation**: recompute centrality/community detection when links change
- **Sync processing**: heavy Obsidian vault reconciliation (currently runs synchronously in the browser for potentially hundreds of files)
- **Index building**: rebuild the vector store / inverted index on demand
- **Scheduled jobs**: periodic GitHub commit sync (currently manual), Obsidian auto-sync (currently a browser `setInterval`), embedding refresh
- **Export/render**: PDF export (currently browser-based), bulk markdown rendering

**Integration approach:** A **Python worker process** (Celery + Redis, or a simpler `RQ`/`asyncio` setup for local-first) running alongside the Next.js dev server. The Next.js app posts tasks to a `/api/tasks` route that forwards to the Python queue. Results are written back via a callback to a Next.js route that updates Dexie (or the Python service writes directly to a shared SQLite/Postgres that mirrors the relevant Dexie tables). For local-first simplicity, a single Python process with `asyncio` and an in-memory queue is sufficient.

**Priority: 8/10** — Unlocks all other Python opportunities (#1, #4, #5) by providing the execution substrate; fixes the sync performance problem; enables scheduled automation.

### 7. Advanced File Processing & Document Intelligence
**Location:** `src/lib/sync.ts` (`serializeNote`, `parseFrontmatter`, `isBinaryFile`), `src/components/files/files-view.tsx`, `src/lib/ai/attachments.ts` (`prepareAttachment`, `formatFileBlock`), `/api/canvas/embed/route.ts` (reader-text extraction)

**Why Python fits:** File processing is currently rudimentary — YAML-ish frontmatter regex parsing, binary/text classification by extension, and a 4,000-char "reader text" extraction that strips tags with regex. Python's document processing ecosystem is vastly superior: `unstructured` (universal document parser), `pdfplumber`/`PyMuPDF` (PDF extraction with layout), `python-docx` (Word), `openpyxl` (Excel), `beautifulsoup4`/`trafilatura` (real reader-mode extraction), `pytesseract` (OCR), and `librosa` (audio analysis).

**Use cases:**
- **Real PDF parsing**: extract text with layout/tables/figures from synced PDFs (currently just served as binary blobs)
- **Document intelligence**: parse Word/Excel/PowerPoint files dropped into the canvas or synced from Obsidian
- **Web page reader-mode**: replace the regex-based `extractReaderText` in `/api/canvas/embed` with `trafilatura` (purpose-built, far superior)
- **OCR**: extract text from images (screenshots, diagrams, whiteboard photos) — feeds search and RAG
- **Audio transcription**: `whisper` for voice notes synced from Obsidian — creates searchable text
- **Image understanding**: `CLIP`/`BLIP` for image captioning and visual similarity search
- **Code file extraction**: parse source files for symbols, docstrings, type signatures — feeds the architecture graph and search

**Integration approach:** A **FastAPI service** with endpoints like `/parse/pdf`, `/parse/web`, `/transcribe/audio`, `/ocr/image`. The canvas `web-node.tsx` would call `/parse/web` instead of the current regex route. The attachment pipeline (`prepareAttachment`) would call `/parse/*` for non-text files. A **background worker** (#6) processes synced binary files (PDFs, audio, images) and writes extracted text back as searchable content.

**Priority: 8/10** — Unlocks a whole class of content (PDFs, images, audio, Office docs) for search and RAG that's currently invisible to the AI; the web-reader improvement alone is a quick win.

### 8. Multi-Agent Orchestration Framework
**Location:** `src/lib/ai/agents.ts` (`AGENT_ROSTER`), `src/lib/ai/workflow.ts` (`WORKFLOW_STEPS`), `src/components/agents/agents-view.tsx`, `src/components/workflow/workflow-view.tsx`, `src/lib/stores/chat-stream.ts`

**Why Python fits:** The current agent system is a **single-agent loop** (`runWorkspaceChat`, max 8 rounds) with role-swapping via system prompts. The 16-step workflow is a linear chain. Python's multi-agent frameworks (`LangGraph` for stateful agent graphs, `CrewAI` for role-based crews, `AutoGen` for conversational agents, `swarm` for handoffs) enable far more sophisticated orchestration: agents that talk to each other, parallel execution, dynamic routing, human-in-the-loop checkpoints, and complex DAGs.

**Use cases:**
- **Parallel workflow steps**: the 16-step pipeline is currently strictly sequential — Python could run independent steps concurrently (e.g., "design" + "data model" + "API" in parallel)
- **Agent debate/review**: the reviewer agent critiques the programmer agent's output, which revises — multi-turn conversation
- **Dynamic routing**: route a task to the right agent based on content analysis (not a fixed 16-step order)
- **Human-in-the-loop**: pause the workflow at a checkpoint, surface a decision to the user, resume
- **Agent memory**: persistent memory across runs (the `Memory` table exists but isn't used for agent memory) — Python could implement episodic/semantic memory
- **Self-reflection loops**: agent evaluates its own output, retries if quality is low (the current "empty response guard" is a crude version of this)
- **Crew execution**: the 7 agents collaborate on a single task with defined roles and handoffs

**Integration approach:** A **FastAPI service** running `LangGraph` (or `CrewAI`) that exposes `/agents/run` and `/agents/stream` (WebSocket for live streaming). The browser's `runWorkspaceChat` loop is replaced with a call to the Python orchestrator for complex multi-agent tasks, while keeping the simple single-turn chat path in the browser for low-latency interactions. The Python service calls back into the Next.js `/api/chat` proxy (or directly to the provider) for LLM calls, and uses the same `WORKSPACE_TOOLS` interface (exposed via a Next.js `/api/tools/execute` route) to mutate the Dexie DB.

**Priority: 7/10** — Significant UX upgrade for power users; the linear 16-step pipeline is the main limitation of the workflow feature; multi-agent debate would improve output quality. But it's complex and the current single-agent loop works well enough for most cases.

## TIER 3 — Valuable Additions (Priority 5–7)

### 9. Git/GitHub Intelligence Service
**Location:** `src/app/api/github/route.ts` (Octokit proxy), `src/lib/github-sync.ts` (`syncGithubCommits`, `extractSpecRefs`), `src/components/dashboard/commits-panel.tsx`, `src/lib/db/schema.ts` (`Commit`)

**Why Python fits:** GitHub integration is currently **pull-on-demand** — the user clicks "sync" and gets a flat list of commits with file names. There's no diff analysis, no semantic understanding of changes, no webhook integration, no CI/CD awareness. Python's `GitPython`/`pygit2` for local repo analysis, `PyGithub` for API enrichment, and NLP for commit message understanding would make this a real engineering intelligence tool.

**Use cases:**
- **Semantic commit analysis**: classify commits (feature/fix/refactor/test/docs/chore) using NLP on the message + diff
- **Auto-linking**: beyond the current `RFC-\d{1,4}` regex, use semantic similarity to link commits to specs/tasks ("this commit's diff touches combat code → link to the Combat spec")
- **Diff summarization**: generate `aiSummary` for commits using an LLM (the field exists but is manually annotated)
- **Impact analysis**: "this commit modified files in 3 systems — here's the blast radius"
- **Webhook server**: a Python webhook receiver for push/PR events → automatic sync without manual clicking
- **Trend analysis**: velocity, hotspots, churn analysis over commit history
- **PR integration**: pull request review, status checks, merge management

**Integration approach:** A **FastAPI service** with a `/webhook/github` endpoint (receives GitHub webhooks) and `/analyze/commit` (accepts a commit SHA, returns semantic analysis). The existing `/api/github` proxy remains for the basic Octokit calls. A **background worker** processes new commits: fetches the diff, runs semantic analysis, updates the `Commit.aiSummary` and auto-links. The webhook server replaces the manual "sync" button with real-time push.

**Priority: 7/10** — The `aiSummary` field is already in the schema and used by the context engine; auto-populating it would meaningfully improve the AI's understanding of project history. Webhook integration removes friction.

### 10. Workflow Pipeline State Machine & Persistence
**Location:** `src/lib/ai/workflow.ts` (`WORKFLOW_STEPS`, `buildStepPrompt`), `src/lib/db/repos/workflow.ts` (`createRun`, `updateStep`), `src/components/workflow/workflow-view.tsx` (`runStep`, `runAll`, `autoAdvance`)

**Why Python fits:** The 16-step workflow is currently orchestrated **entirely in the browser** — `runStep` chains calls, `priorOutputs` accumulates context, and state lives in Dexie `WorkflowRun`/`WorkflowStep` rows. If the browser tab closes, a run is lost mid-flight. There's no branching, no retry-with-modification, no resume-from-checkpoint, no parallel branches. Python's workflow engines (`LangGraph` with checkpointing, `Prefect`/`Dagster` for data pipelines, `temporal` for durable execution) provide durable, resumable, observable workflows.

**Use cases:**
- **Durable execution**: a workflow run survives browser refresh/close; resumes on reconnect
- **Checkpointing**: save state after each step; resume from any step
- **Branching workflows**: not all 16 steps are needed for every project — dynamically skip/include based on earlier outputs
- **Retry with modification**: if a step's output is poor, retry with a modified prompt (the current "empty response guard" just errors)
- **Parallel execution**: run independent steps concurrently
- **Workflow templates**: different pipelines for different project types (game vs. web app vs. API)
- **Observability**: step timing, token usage, cost tracking per run

**Integration approach:** A **FastAPI service** running `LangGraph` (with `MemorySaver`/`SqliteSaver` for checkpointing) or `Temporal` (for production durability). The browser calls `/workflow/start` → gets a run ID → polls or subscribes via WebSocket for step updates. The Python service calls the LLM provider directly (or through the existing `/api/chat` proxy) and writes step outputs back. The `WORKFLOW_STEPS` definition moves to Python as a `StateGraph`. The browser's `workflow-view.tsx` becomes a thin UI over the Python-managed state.

**Priority: 6/10** — Solves the "lost run on tab close" problem and enables branching/parallel; but the current linear pipeline works and the browser-based execution has the advantage of local tool execution.

### 11. Real-Time Collaboration & WebSocket Server
**Location:** `src/lib/canvas-collab.ts` (`CanvasOp`, `Transport` interface, `LocalOnlyTransport`, `resolveConflict`), `src/components/canvas/canvas-board.tsx`

**Why Python fits:** The codebase already has a **collaboration architecture seam** — `CanvasOp` operations, a `Transport` interface, conflict resolution — but it's backed by a `LocalOnlyTransport` no-op. The canvas is designed for real-time multi-user editing but has no server. Python's `websockets`/`FastAPI WebSocket` + `redis` pub/sub, or a full CRDT engine (`Y.py` mirroring Yjs), would activate this dormant feature.

**Use cases:**
- **Real-time canvas co-editing**: multiple users see each other's nodes/edges live
- **Presence awareness**: see who's editing which note/spec/task
- **Shared AI agent sessions**: multiple users watch an agent run and can intervene
- **Live dev-log stream**: team members see commits/agent actions in real time
- **Conflict resolution**: operational transform or CRDT-based merge (currently last-write-wins)

**Integration approach:** A **Python WebSocket server** (FastAPI + `websockets`, or `socket.io` Python server) that brokers `CanvasOp` messages between connected clients. For CRDT-based merging, `Y.py` (Yjs Python port) would sync with the browser's Yjs instance. The existing `Transport` interface is the integration point — implement a `WebSocketTransport` that connects to the Python server. Auth via the same local-first model (no accounts needed for local network).

**Priority: 6/10** — The seam is already built; activating it is relatively low-effort. But MasarFlow is currently single-user/local-first, so collaboration may not be a near-term product goal.

## TIER 4 — Specialized/Infrastructure (Priority 3–5)

### 13. Filesystem Watcher Enhancement (Content-Aware)
**Location:** `src/app/api/watch/route.ts` (fs.watch SSE), `src/lib/watcher.ts` (`inferFileType`, `matchSystemByPath`), `src/components/watcher/watcher-view.tsx`

**Why Python fits:** The watcher streams raw file events (created/modified/deleted) with basic type inference and system matching. It doesn't analyze *what changed* in the file. Python's `watchdog` library (more robust than Node's `fs.watch`), plus content analysis (AST diff, symbol extraction), would make the watcher intelligent.

**Use cases:**
- **Content-aware events**: "function `calculateDamage` was added to `combat/core.py`" instead of just "modified"
- **Symbol tracking**: extract function/class/module definitions on change → auto-update the architecture diagram
- **Impact propagation**: "this file is imported by 12 others — flag as high-impact change"
- **Test detection**: "a test file was modified — likely related to the spec it tests"
- **More robust watching**: `watchdog` handles platform quirks better than `fs.watch`

**Integration approach:** Replace the Node `/api/watch` route with a **Python SSE endpoint** (FastAPI + `watchdog`). The existing `EventSource` client works unchanged. The Python watcher enriches events with content analysis before emitting them. A **background worker** parses changed files and writes symbol/impact metadata.

**Priority: 5/10** — The current watcher works; content awareness is valuable but depends on #4 (code analysis) being implemented first.

### 14. Obsidian Sync Engine (Robust Reconciliation)
**Location:** `src/lib/sync.ts` (`reconcile`, `classifyRemoteStatus`, `hashContent`), `src/components/sync/sync-view.tsx` (`handleScanObsidian`, `handleSyncObsidian`, `handlePullObsidian`), `src/lib/obsidian-client.ts`

**Why Python fits:** The sync engine is a custom 3-way merge with FNV-1a hashing and last-write-wins conflict resolution. It runs entirely in the browser, synchronously, for potentially hundreds of vault files. Python's sync libraries (`gitpython` for Git-like 3-way merge, `diff3`-based merging, `mercurial`'s merge logic) and async I/O would make it robust and non-blocking.

**Use cases:**
- **Semantic 3-way merge**: merge note bodies at the paragraph/line level instead of whole-file overwrite
- **Async batch sync**: process hundreds of files concurrently with `asyncio`
- **Conflict visualization**: generate proper diff views for manual conflict resolution
- **Sync history**: maintain a sync log for undo/rollback
- **Selective sync**: sync only specific folders based on rules

**Integration approach:** A **FastAPI service** that the browser calls instead of doing sync in-component. The `handleSyncObsidian`/`handlePullObsidian` logic moves to Python. The browser just calls `/sync/push` and `/sync/pull` and renders results.

**Priority: 4/10** — The current sync works for typical vault sizes; the whole-file conflict resolution is acceptable for a single-user local-first tool. Valuable only for large vaults or multi-user scenarios.

**Priority: 4/10** — Useful but not core; the browser-based export is adequate for most users.

### 16. Plugin Sandbox & Extension Runtime
**Location:** `src/lib/plugins.ts` (`PLUGIN_CATALOG`, 12 plugins), `src/lib/plugins-runtime.ts` (`usePlugin`), `src/lib/canvas-registry.ts` (`registerCanvasCardType`), `src/components/plugins/plugins-view.tsx`

**Why Python fits:** Plugins are currently **static catalog entries** (hardcoded `PluginDef`s) that toggle features on/off via settings. There's no dynamic plugin loading, no sandboxed execution, no plugin marketplace. Python could provide a **secure plugin runtime** — loading plugins as Python scripts, executing them in a sandboxed environment, and exposing a richer plugin API (custom tools, custom analysis, custom exporters).

**Use cases:**
- **Custom AI tools**: plugins can define new workspace tools (beyond the 40 built-in ones) that the agent can call
- **Custom analysis plugins**: "analyze my game's balance spreadsheet" → a Python plugin that parses CSV and computes balance metrics
- **Custom exporters**: plugins that export to domain-specific formats
- **Custom canvas node types**: plugins that render specialized canvas cards (e.g., a dialogue-tree editor for game dev)
- **Plugin marketplace**: download and install community plugins (Python scripts) with sandboxed execution

**Integration approach:** A **Python plugin runtime** that loads `.py` plugin files from a `plugins/` directory, each implementing a defined interface (`on_event`, `custom_tools`, `custom_analysis`). A **FastAPI service** exposes the plugin API. The existing `usePlugin` hook checks if a Python-backed plugin is active and calls the Python service for its functionality.

**Priority: 3/10** — The plugin system works well as a settings-toggle system; dynamic Python plugins add complexity and security concerns. Only valuable if MasarFlow wants to become an extensible platform.

## Recommended Implementation Order

**Phase 1 (Foundation):** #3 (Local LLM/Ollama) → #6 (Worker Queue) → #1 (Embeddings) → #2 (RAG)
*These four form a cohesive Python AI runtime that upgrades every AI feature in the app. The local LLM removes the API-key barrier, the worker queue provides background processing, embeddings enable vector search, and RAG replaces the context-stuffing engine.*

**Phase 2 (Intelligence):** #4 (Code Analysis) → #5 (Graph Analysis) → #7 (File Processing) → #9 (Git Intelligence)
*These add analytical depth — real static analysis, graph algorithms, document parsing, and commit understanding.*

**Phase 3 (Advanced):** #8 (Multi-Agent) → #10 (Workflow State Machine) → #11 (Collaboration) → #12–16 (Specialized)
*These are power-user features that build on the foundation.*

## Key Architectural Note

MasarFlow's **local-first, browser-centric architecture** is both the biggest constraint and the biggest opportunity for Python integration. The constraint: there's no server-side persistence, so Python services need their own storage (SQLite/ChromaDB) synced from the browser's Dexie via a small sync API. The opportunity: the `/api/chat` proxy pattern is already established — adding Python services behind Next.js API routes follows the exact same architecture. The browser's `runWorkspaceChat` agentic loop, the `WORKSPACE_TOOLS` belt, and the `assembleWorkspaceContext` engine are all well-defined seams that Python can either replace or augment without touching the React UI.
