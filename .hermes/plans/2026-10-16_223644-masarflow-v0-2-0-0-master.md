# MasarFlow v0.2.0.0 — "Desktop" Overhaul — MASTER PLAN

> **For Hermes:** execute with `subagent-driven-development`, one task at a time, two-stage review per task.
> This master file holds the vision, verified findings, architecture decisions, contracts, phase map and risks.
> The executable tasks live in the phase files listed in §7. **Read this file fully before opening any phase file.**

**Goal:** Turn MasarFlow from "a Next.js web app plus a separate Electron launcher" into one installable desktop application that feels like Hermes Desktop (chat-first agent workspace) fused with Obsidian (local markdown vault, backlinks, graph, canvas) and GitHub (git + issues + PRs + CI), where every page shares one entity graph so the AI chat knows everything the user is working on — and where every shipped feature is proven to work by an automated test.

**Branch:** work on `release/v0.2.0` (created in P0). `main` stays the stable v0.1.x line until the release gate in §3 passes.

## 4. Architecture decisions (with rejected alternatives)

**D1 — One app.** The Electron app *is* MasarFlow. Its window hosts the existing Next app (`src/`). The separate launcher renderer is retired; its useful parts move into the app: terminal → dock panel (P8), env/config → Settings → System + AI Providers (P10), diagnostics → Control Center (P10), setup/clone → replaced by the installer.

**D2 — Embedded server, custom scheme, stable origin.** Next is built with `output: "standalone"` and run inside an Electron `utilityProcess` on `127.0.0.1:<ephemeral port>` with a per-launch random token. The `BrowserWindow` loads `masarflow://app/`; a privileged-scheme handler (`protocol.handle`) proxies each request to the loopback server and injects the token header. *Why:* keeps 100 % of existing code and all 41 API routes; the **origin never changes**, so IndexedDB survives restarts (a random port would change the origin and silently lose all data). *Rejected:* static export (API routes need Node), fixed port (collisions + origin drift), full IPC rewrite (months of work, revisit in 0.3), Tauri (Rust rewrite).

**D3 — Dev parity.** `pnpm dev:desktop` = `next dev` + Electron loading `http://localhost:3000` directly (HMR works; dev IndexedDB is separate from prod).

**D4 — Security model.** Layered: (a) bind loopback only; (b) every request needs the launch token (renderer never sees it — main injects it); (c) Host header allow-list (anti DNS-rebinding) and Origin allow-list (anti CSRF); (d) any filesystem root a route receives must be in a main-process-owned `roots.json` (written only by the native folder picker); (e) Electron hardening (sandbox, contextIsolation, navigation lock, CSP, permission handler); (f) secrets via `safeStorage`. *Deferred:* HMAC per-command approvals (token + allow-list already stop non-renderer callers).

**D5 — No Python in the default product.** Embeddings run in a renderer Web Worker via `@huggingface/transformers` (ONNX/WASM) with the **same model** (`all-MiniLM-L6-v2`, quantized, ~23 MB, bundled — works offline). Vectors are stored in Dexie; search is brute-force cosine in the worker. `python-service/` is deprecated: removed from startup and installer, deleted in 0.3.

**D6 — IndexedDB stays system of record in 0.2** (rewriting 28 repos + 72 live queries to SQLite is too risky). Safety comes from automatic rolling backups (P4) and a user-visible **markdown vault mirror** (P7) so notes/specs/docs/tasks exist as plain files that Obsidian, VS Code and git can open.

**D7 — One entity graph.** A single `EntityRef` (`kind`,`id`,`projectId`), one registry (label/icon/route/param/panel), one `openEntity()` that goes through the dock, one `EntityChip`. What the user is looking at (`ActiveContext`) is **derived from the dock state** — pages publish nothing — and every write is recorded by Dexie hooks into an `activity` table (no separate event bus: `useLiveQuery` already propagates changes to every page).

**D8 — Chat awareness.** The prompt builder receives: (1) *Currently open* (active context), (2) snapshot v2 (adds links, canvases, agents, linked projects, activity, git), (3) semantic RAG over **all** kinds incl. project source files. Tool parity: new tools `get_active_context`, `open_entity`, `get_backlinks`, `list_activity`, `link_entities`; they come from the same `workspace-tool-defs.ts`.

**D9 — Git/GitHub native.** Local git = main-process service using `execFile("git", args[])` (no shell) inside registered roots, with pure output parsers. GitHub = existing Octokit with a PAT in `safeStorage` (OAuth device flow is an open question). Issues⇄Tasks two-way sync, PR + check-run status, commit⇄task linking.

**D10 — Feature truth is enforced by tests**, not by promises: plugin-consumer guard, dead-route guard, setting-consumer guard, feature matrix ↔ Playwright titles guard — all use one `expectShrinkingAllowlist` helper whose allowlists must reach empty by P9.

**D11 — Versioning.** Package versions become valid semver **`0.2.0`** (electron-builder/electron-updater require it). Git tag and UI display use the project's existing 4-part style: **`v0.2.0.0`** (`APP_DISPLAY_VERSION = "0.2.0.0"`). Future releases: decide whether to keep 4-part tags (updater only reads package semver) — see Q8.

**D12 — Platforms.** Windows x64 is first-class for 0.2.0.0 (NSIS installer + portable). macOS/Linux are *not* validated here (no machine to test) — build config is kept compatible, shipping them is a decision for Q4.

## 6. Conventions for every task

- **TDD cycle, always:** write the failing test → run it, see the stated failure → implement minimally → run, see PASS → commit. Pure logic lives in node-testable modules; UI/Electron glue is verified by the smoke/e2e commands given in the task.
- **Commit per task**, conventional style (`feat(desktop): …`, `fix(dock): …`, `test(guard): …`). Never `git push`, never rewrite history; push is the owner's call.
- **Shell:** this machine's terminal is git-bash. Use POSIX commands and forward-slash native paths. Keep each terminal call small (the host rejects oversized compound commands) — run multi-step checks via small scripts.
- **Verify Electron/Next APIs against the installed packages**, never memory: `grep -n "<symbol>" desktop/node_modules/electron/electron.d.ts`, and `node_modules/next/dist/docs/`. Electron 43 and Next 16.3 post-date most training data.
- **Shell shell duplication is gone:** after P1 there is exactly one sidebar/topbar (in `src/components/shell/`). Do not recreate the desktop copy.
- **Test layout:** `tests/unit/**` (root vitest, alias `@` → `src`, `@desktop` → `desktop/src/main`, `@desktop-shared` → `desktop/src/shared`, added in P1.T1); e2e in `tests/e2e/**`. Test file mirrors source path.
- **No new feature without an entry** in `tests/e2e/feature-matrix.json` (enforced from P0).
- **Dexie:** every schema change = a new `this.version(N).stores({...})` in `src/lib/db/index.ts` (never edit an old version). Current is 10; P3 adds 11 (`embeddings`), P5 adds 12 (`activity`), P6 adds 13 (task `externalRef` is a non-indexed field → no schema bump; `gitRepos` if needed).

## 8. Risks & open questions

**Risks**
- **R1 pnpm + standalone + electron-builder (Windows symlinks).** Mitigation: Spike S1 with `cpSync(..., {dereference:true})`; fallback `node-linker=hoisted` for the build step only.
- **R2 Streaming through `protocol.handle`** (SSE chat, bridge, watcher) and redirects. Mitigation: Spike S2; fallback = fixed per-install port persisted in settings + `session` partition (documented origin-drift risk).
- **R3 WASM embeddings** speed and CSP (`wasm-unsafe-eval`). Mitigation: Spike S3 with a measured budget; fallback = embed in `utilityProcess` via `onnxruntime-node`.
- **R4 Scope.** ~10 phases. Mitigation: cut lines above; each phase ends with a green gate and a commit; releasable alpha after P5.
- **R5 Data loss during migration.** Mitigation: P4 ships before any destructive change; Dexie upgrades are additive only; fixture-based import test from a v10 export.
- **R6 Hide-to-tray on close** confuses new users → default OFF for fresh installs (P10).
- **R7 Untested platforms** (mac/Linux) — see Q4.
- **R8 My API knowledge of Electron 43/Next 16.3 may be stale.** Every Electron/Next task starts with a `grep` of the installed typings/docs (see §6).

**Open questions (defaults used if unanswered — change before the relevant phase)**
- **Q1** Delete `python-service/` now or keep deprecated one release? *Default: remove from startup/installer, keep folder, delete in 0.3.*
- **Q2** GitHub auth: PAT only (default) or OAuth device flow (needs a registered OAuth App `client_id` you own)?
- **Q3** Windows code signing certificate available? *Default: unsigned; SmartScreen warning documented in README.*
- **Q4** Ship macOS/Linux builds in 0.2.0.0? *Default: no — Windows only.*
- **Q5** ~~OpenCode~~ **Decided 2026-10-17: OpenCode is dropped.** Chat connects to models the Hermes way (see P1b). Open sub-questions: Q-P1b-1 file-undo ledger, Q-P1b-2 OAuth/subscription providers. *Defaults in P1b.*
- **Q6** Telemetry/crash reporting? *Default: none; local logs + "Copy diagnostics" only.*
- **Q7** Real-time multi-user collaboration is **out of scope** (removing `canvas-collab`). Confirm.
- **Q8** Version scheme after 0.2.0.0: keep 4-part tags with 3-part package semver, or move to plain semver?
- **Q9** Keep running in a browser (`pnpm dev`) supported? *Default: dev-only; desktop is the product.*
- **Q10** Ship a small `v0.1.6.0` release on `main` whose only change is **Export backup**, so existing v0.1 users can carry their IndexedDB data into 0.2 (different origin, `masarflow://app`)? *Default: yes (P4.T7).* Without it, v0.1 data cannot be migrated.
- **Q11** Ship the semantic index as best-effort (default) or block the UI until the model has loaded? *Default: best-effort — the app is usable immediately; search falls back to Fuse until the index is ready.*

## 10. Handoffs between phases

**P5 → P9: features P9's Playwright specs must cover.** Add each to `tests/e2e/feature-matrix.json` *in the same commit as its spec* (the P0 guard rejects a listed feature without a spec titled `"<route>: <feature>"`, so P5 must not add them early):

- `/chat: chat knows the open page` — open a task, ask "what am I looking at?", the reply names the task.
- `/chat: create task from message` — click "Create task from this message"; Task Boards opens on the new task.
- `/brain: wikilinks open in preview` — `[[Other note]]` in preview mode opens that note.
- `/brain: connections list` — a note linked from a task shows the task chip; clicking it opens Task Boards.
- `/tasks: task done writes a dev log` — set a task to done; `/devlogs` shows `Completed task "…"`.
